# Rubric: is this plan ready to post and build from?

Every row is a disqualifier: the default grade is pass, and a row fails only on a fact you can quote from the package (for plan-executable and test-plan-observable, a quoted absence counts). Judge substance, never form: length, headings, section names, tone, and polish decide nothing. A terse plan can be ready; a long, confident, well-formatted plan can be wrong or unbounded. Partial or untitled sections are valid input: grade what is there.

Premise: every package is AI-assisted work (the course's students build with AI tools). The premise decides one thing only, whether an AI-use disclosure was owed. Where the stated policy requires disclosure for issue comments, or for all AI use in any form, a plan comment without a disclosure fails; where the policy places disclosure only on the pull request, a comment without one passes. Grade the obligation at the stage the policy names, and never invent one the policy text does not state. The premise never tells you who wrote a sentence, and style is never evidence of authorship.

Evidence outranks claims: when a run in the repro evidence conflicts with a cause stated in the issue, the thread, or the plan, the run wins, whoever made the claim. A role-holder is a thread participant labeled with a repo role (owner, member, collaborator, or contributor); anyone else's comment is context, not direction.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diagnosis-grounded | The plan's stated cause and the component, stage, or flag it blames, read against every step, control, contrast, and diagnostic run in the repro evidence, and against causes role-holders state in the thread highlights. See "Diagnosis and grounding" in references/evidence-guide.md. | Pass unless you can quote one of these. (a) A RUN RULES IT OUT: the defect persists in a run where the blamed part is absent or bypassed; or the blamed part runs under the very conditions the plan says trigger the defect and works correctly; or a step shows the defect already present before the blamed stage runs (so a change at or after that stage, such as rebuilding lost data afterwards, only patches the symptom). (b) A ROLE-HOLDER'S CAUSE IGNORED: a role-holder names a more specific or different cause that no run contradicts, and the plan neither adopts it nor says why it disagrees. Taking a cause from the issue or thread never shields a plan from (a). Not failures: a control that removes a condition the plan's cause depends on (the cause predicts that result); a run the plan explains in terms of its own cause, unless another run contradicts that explanation; a guard or clamp at the exact site where the evidence shows the failure; a cause that restates the issue's or thread's diagnosis when no run contradicts it. | required |
| scope-bounded | Every change the plan and comment propose (every list item and aside, not only the summary), read against the behavior the Issue section reports. See "Scope". | Pass unless the proposed work includes at least one of: a refactor, rewrite, restructure, or module split the reported fix does not need; a dependency, library, or runtime swap, or a version upgrade, beyond what the fix needs; a new user-facing option, flag, setting, prop, or public API; the fix for a different bug (another issue, or a symptom the plan itself treats as separate) folded into the same change; a redesign, new abstraction, framework, or test-harness migration applied beyond the broken path. A hedged aside proposing extra work ("maybe also", "might also", "while at it") counts as proposed work. Not failures: work named and deferred (left out, split into its own issue, or left to a follow-up or the maintainers' call); work the issue or a role-holder's direction asks for; auditing sibling sites in the same function or file for the same defect; regression tests and docs for the fix itself; an honest scope-down that fixes a stated slice (one platform, one variant) and names what it leaves out; offering tests or review to an existing PR. | required |
| plan-executable | The plan's chosen approach and every file, function, module, or code path it names, read for whether a stranger could start work without asking the author anything. See "Executability". | Pass unless you can quote one of these. (a) NO CHOSEN APPROACH: what the change will do is left to investigation ("investigate and fix whatever turns up", "profile and optimize", "try options and see", "fix it once the cause is clear"). (b) NO PLACE TO START: no file, function, module, component, or code path is named anywhere in either draft. (c) AN OPEN FORK: a real choice between approaches or locations is left unmade where work would start ("upstream or vendored, whichever is easier", "which layer? not sure", a change placed "somewhere"). Not failures: naming the subsystem or code path (one component, or both sides of one boundary such as client and server) and the mechanism of the change, and stating that the exact function or line will be pinned during the build; an unknown about the exact site (one layer or level up or down, which of two adjacent call sites) once the mechanism is chosen; a chosen default with a fallback that a named measurement or review decides; a terse plan naming one file and one concrete change. A "which layer" unknown is (c) only when no mechanism is chosen. | required |
| test-plan-observable | The plan's test-plan sentences, titled or not, read against the repro evidence's steps and artifacts. See "Test plan". | Pass unless the test plan names no outcome that is both observable (a value, output, exit code, rendered state, count, timing bound, or the absence of a named error) and tied to the reported behavior. It fails when it offers only a feeling ("should feel fast", "nothing should feel broken", "should look better"), only a suite run ("run the full test suite", "make sure nothing regresses") with no check of the fixed behavior, or only a restatement of the goal ("it works", "the bug is fixed") with no step that would show it. Not failures: re-running the repro and naming what must now come out differently; a named regression test for the reported case; a suite run alongside such a check; brevity. | required |
| honesty-of-claims | Sentences in the plan and comment that assert certainty (confirmed, verified, definitely, the root cause is, no risk), read against what the repro evidence and the thread establish. See "Honesty". | Pass unless you can quote a sentence presenting as certain or verified a claim (a cause, the fix's completeness, compatibility, the absence of risk, a report or result being posted) that the package's own evidence contradicts or shows was never checked, with no hedge anywhere in the package disclosing the gap. Not failures: a plainly stated cause that fits every run in the evidence; a claim about the code that nothing in the package contradicts; a flagged unknown, risk, estimate, or open question; confidence the repro run itself warrants. | required |
| thread-aware | Both drafts, read against the thread highlights: role-holder direction, and any patch, test build, branch, or PR already in flight on the same behavior (whoever opened it). See "Comms". | Pass unless you can quote one of these. (a) DIRECTION IGNORED: a role-holder gives explicit direction on this behavior (names the culprit, sets or rejects an approach, asks for something to be tested), and neither draft acknowledges it, or the plan takes a path that direction rejected without saying why. (b) IN-FLIGHT WORK IGNORED: a patch, test build, branch, or PR on the same behavior is in the thread, and neither draft acknowledges it. Not failures: adopting the direction; offering to test, review, or add tests to the in-flight work, or to rebase onto it if it lands first; naming it and explaining a different or narrower path; a thread with no direction and no in-flight work (silence passes). | required |
| repo-conventions-met | The repo-facts block's contribution policy and AI-use wording (live: the repo's CONTRIBUTING file, templates, and any AI policy file), read against both drafts. See "Comms". | Pass unless you can quote one of these. (a) MISSING REQUIRED DISCLOSURE: the policy text requires AI use to be disclosed for issue comments, or for all AI use in any form without limiting that to pull requests, and neither the plan nor the comment has a sentence stating that AI assisted the work. (b) POLICY BROKEN: the plan or comment explicitly proposes to skip or break a stated requirement other than disclosure. Not failures: disclosure asked only on pull requests, commits, or releases (a plan comment is not a pull request); a policy asking for human authorship, review, understanding, or comments in the contributor's own words without asking that AI use be stated; a policy silent on AI; any disclosure sentence, however brief; an own-words or no-fully-generated rule, which the premise never shows broken. | required |

## Verdict rule

All seven checks are required; there is no preferred row. Accept when every check is graded pass, or graded unclear and counted as pass under its rule below. Reject when any check is graded fail, or graded unclear and counted as fail. The verdict is binary: there is no third outcome.

Use unclear only when the recorded fact leaves real doubt whether a fail limb applies, never to dodge a call the pass condition settles. Check each row's Not-failures list first: a case it describes is a pass, not unclear. Unclear is treated per check:

- diagnosis-grounded, scope-bounded, honesty-of-claims, thread-aware: unclear counts as pass. Each is a disqualifier, so a fault you looked for and could not quote did not fire.
- plan-executable, test-plan-observable: unclear counts as fail. Each asks whether a stranger could build or verify from the package, and a doubt the package leaves open means that bar is not cleared.
- repo-conventions-met: unclear counts as pass for limb (b) and for policy wording that is ambiguous about AI disclosure. Limb (a) is never unclear: when the policy plainly states the obligation and neither draft discloses, grade fail.

Grade and report all seven checks even after one fails. Each evidence line quotes the fact that decided the grade and, for a fail, names the limb that fired, for example "(a) ...". Never fail a check on length, formatting, tone, or confidence alone.
