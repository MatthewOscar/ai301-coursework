# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| repo-alive | The Repo facts repo line (the archived flag), the "last push to any branch" date, and the "captured:" date in the bundle header. | Pass when the repo line says archived: no AND the last push is within 365 days of the captured date. Fail when archived says yes, or when that gap exceeds 365 days. Quote both dates and the gap in days. Nothing else decides this row. NOT failures: "latest release: none published", or a release far older than the last push, because push and release recency routinely disagree on healthy projects; a low star count; a large open-issue count, which is volume, not death; a commit list dominated by bots. NOT a rescue: fast maintainer reply times never save a repo that is archived or long unpushed, so read the archived flag and the push date before any latency number. | required |
| maintainers-active | The "last 5 default-branch commits" list (each date and author), the "maintainer first-response sample", and any OWNER, MEMBER or COLLABORATOR comment in this issue's thread, all read against the captured date. | Pass if ANY ONE holds: (a) one of the last 5 commits is within 180 days of the captured date and its author is a person rather than an automation account (a login ending in [bot], or a dependabot, pre-commit, CI, prow or auto-merge service account); (b) one of those commits within 180 days is a bot merging a named human's pull request, which is project life even though a bot pushed it; (c) the first-response sample gives a numeric days figure for an issue opened within 365 days of the captured date; (d) an owner, member or collaborator has commented in this issue's thread. Fail only when none holds. NOT failures on their own: a sample with only one or two entries, or one where every line reads "no maintainer comment in thread", because a project with a large open-issue backlog is drowning, not dead. NOT project life: a commit list that is purely automated dependency or version-bump churn with no human author and no human pull request merged; nor a latency figure drawn only from issues older than 365 days, which describes a project's past, not its present. | required |
| policy-permits | The "contribution policy" line under Repo facts, including any quoted CONTRIBUTING or AI-policy text and the section name it cites. | Pass unless that line bans AI-assisted contribution outright. Fail ONLY on a sentence that refuses AI-written work with no permitted form of AI use left open — the archetype being a flat "we do not accept AI-generated code or documentation". Such a sentence is a ban even when the same policy warmly invites people to ask for help, because an invitation to ask a human is not an allowance to use AI. Everything else passes. CONDITIONS ARE NOT BANS: requirements to disclose, to personally understand, test and be able to explain every change, to human-review AI output, and the practice of closing pull requests that appear untested, not understood or machine-translated, are terms to follow, not prohibitions. Discouragement is not a ban: "strongly discourages", or calling AI output often inaccurate, without refusing it. SILENCE PASSES: "no CONTRIBUTING.md in the repo", "no stated policy", and "no statement on AI or contribution tooling" all pass, because the absence of a restriction is not a restriction. A repo shipping AGENTS.md for AI agents is a positive signal and passes. A policy refusing only fully or wholly AI-generated work while expressly allowing assistive AI use is a condition and passes. Do not soften an explicit refusal into discouragement, and do not harden a condition into a ban. | required |
| unclaimed | The "this issue:" line under Repo facts (the assignees field and every linked PR with its state), every claim or pull-request announcement in the visible comments with its date, and the captured date. | This row reads two kinds of evidence and treats them differently. STRUCTURAL FACTS are current state at capture and carry no date of their own, so the age window never forgives them: fail when assignees is anything other than none, or when a linked PR carries the state open (including a fork PR written owner/repo#N (open)). DATED STATEMENTS are forgiven by age: apply the window FIRST, so any claim comment more than 180 days before the captured date leaves this row passing, however many such comments exist and whatever the last visible comment happens to be. After that window, fail when an owner, member or collaborator says the work is reserved for a named person or that other contributions are not wanted; or when a comment within 180 days of the captured date says its author is working on it or announces a pull request they opened, with nothing later in the visible thread ending that claim. Otherwise pass, quoting both dates and the gap in days. NOT live claims, grade pass: linked PRs that are all closed or merged, since a closed unmerged PR is an abandoned attempt and if anything evidence the issue is free; "linked PRs: none" and "none formally linked"; years of claim-and-unassign cycles where assignees now reads none; a bot unassignment, inactivity or stale notice; an unanswered "can I work on this", "is this still open", or an offer to help that asks for guidance rather than announcing work; a maintainer merely encouraging someone to try. ONE exception: a bot warning that an assignee will be auto-unassigned in a few days does not cancel an assignment still in force. Truncation of a thread never makes this row unclear and is never evidence of a hidden claim. | required |
| scope-bounded | The issue title and body, even when truncated, and the visible comment thread. | Pass unless the bundle shows one of these five, which you must be able to quote. (a) A tracking, umbrella or mega issue whose body is largely a list of OTHER issue numbers to pick work from. (b) An open-ended standing campaign with no endpoint, inviting many contributors to keep sending work across the codebase with the contributor choosing the target. (c) An issue whose PRIMARY deliverable is architectural or performance rework of internals — the re-architecture itself is the ask (rewrite this subsystem, parallelise this engine, change this data structure across the codebase), with no reported malfunction driving it. Apply a single test: if you removed the internals work, would anything remain for the issue to deliver? If nothing remains, this disqualifier fires. A defect report does NOT become this merely because it names candidate causes, proposes optimisations, or lists suggested improvements alongside the fix, however technical those suggestions are and however many of them there are; nor does speculation about where a cause might live. (d) A usage or support question asking for no change to the project. (e) A required input or decision the issue itself leaves open — an explicit TBD on something the work needs, a question asking whether current behaviour is by design, or a sentence saying the design should be confirmed before implementing — AND no owner, member or collaborator comment settles it. A maintainer who defers to the contributor's judgement has not settled it. That list of five is exhaustive. These are NOT scope failures, grade them pass: an enumerated plan of edits inside one repository, however long and however many headings, files, pages or line numbers it names, because coordinated enumerated edits are ONE task; an item in such a plan marked "consider", "lower priority", "perhaps" or "may be worth", which is an optional extra, not a separate issue; a suggested example name, which is not an undecided input; a one-sentence issue, including one from a maintainer, and a list of examples closed by "etc."; a truncated body, a long template, a checklist, acceptance criteria, or a pasted log, traceback or environment dump, which are polish, not size; a bug report stated as wrong behaviour plus what should happen, even when its root cause is unknown and even when it only appears on large or long inputs; a defect report that enumerates candidate root causes, or that offers "additional suggestions" for how the fix might be approached — including suggestions involving threading, parallelism or algorithmic improvement — because the reported malfunction is the deliverable and the reporter's theories about it are optional extras; an issue years old; a question-shaped title a maintainer has already answered. Grade the size of the work asked for, not the polish of the writeup, and never grade this row unclear because the body is truncated. | required |
| project-wants-it | The opener's login and ASSOCIATION on the "opened by" line, the labels list on that line, and whether any OWNER, MEMBER or COLLABORATOR appears in the Comments section. | Fail when ALL FOUR hold at once: the opener's association is NONE or the login ends in [bot]; the labels list reads none; no owner, member or collaborator has commented in the thread; and the ask is a new feature or asset rather than a defect report. Also fail when the issue asks a general-purpose project to ship one outside party's own branding or company-specific asset. Otherwise pass, including every defect report however niche the reporter's workflow, every issue carrying any project label at all, every issue a maintainer opened or replied in, and every request whose author also benefits from the fix. Never fail this row on the requester's motive alone, on the issue's age, on a missing "good first issue" label, or on missing reproduction steps. | required |
| response-latency | The "maintainer first-response sample" block under Repo facts. | Pass when at least one sampled issue shows a first owner, member or collaborator response within 90 days; this takes precedence over sample size, so a qualifying entry passes the row even in a one- or two-entry sample. Only when no entry qualifies does sample quality matter: grade unclear, never fail, when the sample has fewer than three entries or when every entry reads "no maintainer comment in thread", because small samples occur despite the header saying five, and all-silent samples occur on healthy high-volume projects as well as dead ones. Ranking only — this row never changes the verdict, whatever its grade, and a fast reply here never rescues a repo that repo-alive failed. | preferred |

Three conventions apply to every row above.

Anchor every threshold to the bundle's own "captured:" date, never to today. Compute the gap
in days and quote both dates in your evidence line.

The "good first issue" label proves nothing either way. It sits on umbrella issues, on issues
already assigned, and on issues open for years, while clean bounded issues often carry no
such label. Never require it, never read it as evidence of scope, never fail an issue for
lacking it.

Truncation is not evidence. A body ending in "[... truncated]" or a thread header reading
"first M shown" of N means the bundle is incomplete, not that something is hidden. Grade only
what the bundle shows, and never infer an unseen claim, policy, sub-issue or design debate.

## Verdict rule

Accept when every check weighted required is graded pass. Reject when any check weighted
required is graded fail. The verdict space is binary; there is no third outcome.

Preferred checks never change the verdict. Report response-latency with its grade, and on an
accepted issue cite it as a reason to prefer this issue over other accepted candidates. A
preferred check graded fail or unclear never blocks an accept.

How unclear is treated, per check, because the right answer differs by evidence type.

- repo-alive, maintainers-active and unclaimed: treat unclear as fail. Each reads fields
  present in every bundle — the archived flag, the last push date, the last 5 commits, the
  assignees field, the linked-PR states — so a legitimate unclear should essentially never
  arise. A truncated body or thread never makes one of these unclear, because the repo-facts
  lines decide them. If you genuinely cannot read the named field, fail and name it:
  liveness and ownership are the two things a first contributor cannot afford to guess at.
- policy-permits, scope-bounded and project-wants-it: treat unclear as pass. Each is written
  as a disqualifier, so unclear means the bundle did not show the disqualifying evidence, and
  a bundle that truncates bodies and threads must not convict an issue of a problem it never
  exhibits. Grade unclear only when the named evidence is genuinely absent, then pass the row
  and say in the evidence line what was missing.

Grade and report every required check, even after one has already failed. Quote the bundle
line or comment that decided each grade. When two required checks fail, name the first in
table order as the deciding reason.

Do not add checks of your own. None of these may ever produce a fail: the presence or absence
of a "good first issue" label; how old the issue is; star count or open-issue count; how many
people have asked to work on it; missing reproduction steps; the length or polish of the
writeup. If an issue clears all six required checks but still feels wrong, accept it and name
the tension in your summary — the fix belongs in the rubric, not in the run.
