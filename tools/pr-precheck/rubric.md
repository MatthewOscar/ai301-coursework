# Rubric: is this pull request ready to submit?

Every row is a disqualifier. Its default grade is pass, and it fails only on a fact you can quote from the package. In the three test-evidence rows (fix-shown-before-after, test-plan-covered, repo-checks-run), a quoted absence counts as such a fact: quote the issue, plan, or repo item and state that the evidence has no output or outcome for it.

Judge substance, never form. Description length, polish, heading style, enthusiasm, terse wording, and commit count decide nothing. A terse complete PR can be ready, and a beautiful confident one can be hiding drift. Partial or untitled sections are valid input: grade what is there. A description's confidence or checklist never substitutes for reading the hunks.

Honest-outcome rule: a PR that honestly discloses a shortfall, a deferred edge, or a recorded plan deviation can be ready. A deferral that the plan records and the description restates is bounded: it is neither drift nor untested. Never equate 'less than everything' with 'hold'.

Premise: every package is AI-assisted work (the course's students build with AI tools). The premise decides one thing only: whether an AI-use disclosure was owed. Grade that obligation only where the policy text states it. Silence or ambiguity creates no obligation. Never infer AI use from style.

One fault, one home. Debris (debug prints, commented-out code, dead code, TODOs, churn) is graded under diff-reviewable, not diff-matches-plan. Test runs and their outcomes are graded in the test rows, not in claims-match-diff.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-matches-plan | The diff's changed files and hunks (the file map), read against the plan's stated scope, Files list, not-in-scope line, and deviation or limit notes. See 'Plan fidelity' in references/evidence-guide.md. | Pass unless you can quote one of these. (a) UNPLANNED CHANGE: a changed file, or a hunk that changes behavior, that the plan's scope and Files never name and no plan deviation note records. Examples: a new option, flag, setting, or public API; a refactor, rename, or rewrite of code the fix does not need to touch; a dependency or version bump; a second fix; an extra feature. Quote the hunk and the plan line it falls outside. (b) DELIVERABLE OMITTED: a deliverable the plan names (a code change, a docs page, a changelog entry, a test) that no hunk contains, where neither the plan nor the description says it was dropped or deferred. Not failures: tests, changelog or release-note entries, translation strings, and generated files that serve the planned fix, even when the Files list omits them; a helper the planned change calls, inside a planned file; a change a plan deviation note records; a deferral or limit the plan records; an omission the plan or description states. A description that only admits an unplanned change does not re-tie it; only a plan deviation note does. | required |
| claims-match-diff | The description's statements about what the change contains or leaves out, read against the diff's actual files and hunks. Examples: 'exactly the plan', 'nothing beyond', 'no other changes', 'docs updated', 'tests added', 'changelog added', 'no API changes', and checklist ticks. | Pass unless you can quote a description or checklist claim that the diff contradicts, in either direction. (a) It claims nothing beyond the plan, or no other changes, while the diff holds a change that diff-matches-plan would call unplanned. (b) It claims an artifact (a docs page, a test, a changelog entry, a fixture, a translation) that the diff does not contain. (c) It denies something the diff does, such as 'no new options' next to an added option. Not failures: confident tone; a claim the diff supports; a loose count or summary (such as 'one function touched') when the extra lines are helpers or tests serving the described change; a claim about which cases a test covers, when a test for the change exists (test-plan-covered judges coverage); a description that accurately admits extra changes (diff-matches-plan judges those); claims about test runs and outcomes (the test rows judge those); omitting a minor detail. | required |
| fix-shown-before-after | The test evidence, read against the issue's repro, the plan's repro evidence, and the plan's test plan: which path and input are exercised, and what the before and after show. See 'Test evidence'. | Pass unless you can quote one of these. (a) NO EVIDENCE: the test evidence is absent, empty, or '(none provided)'. (b) UNCHANGED PATH: the evidence exercises only a path or input the diff does not change, or only a control or a different scenario than the reported one, and never the reported behavior. (c) ONLY ASSERTS: for the reported behavior there is no repro step or command paired with a concrete after result (captured output, a value, an exit code, a quoted message, a rendered state, a screenshot). What is offered instead is prose that it works ('works now', 'verified working', 'tested locally'), a use anecdote, or a bare suite result. (d) ADMITTED UNTESTED: the description or evidence says the reported behavior was not run, or that the change as a whole is untested. Not failures: a before taken from the plan's repro evidence or the issue, when the after shows the expected result; terse captured output; an after shown as captured output of a test that runs the issue's own repro input; a disclosed untested side case (another platform, a deferred edge) when the reported behavior's before and after are shown. | required |
| test-plan-covered | The plan's test-plan items (each named repro, failure mode, control, platform case, and docs or render check), listed against the test evidence and the tests the diff adds. | Pass unless you can quote a test-plan item that the evidence never mentions, that no test added in the diff covers, and that neither the plan nor the description defers with a reason. An item counts as covered in either of two cases: the evidence names it with an outcome (captured output, or a statement such as 'control unchanged'), or an added test runs that item's input and the suite run is shown. An item is not covered because it shares code with a shown item. If the evidence and the added tests are silent on it, it is absent. Not failures: a plan with no test plan; an item the plan or description honestly defers with a reason; terse wording. | required |
| repo-checks-run | The checks the repo states for a PR or the plan's test plan names (a test suite, formatter, linter, code generator, pre-commit run), from the repo-facts block, the contribution docs, and the plan, read against outcome lines in the test evidence and description. | Pass unless a check those sources state shows no run, or no visible outcome, anywhere in the test evidence or description. A visible outcome is any line stating the result. Examples: 'tests pass (612)', 'fmt and clippy clean', 'go generate produces no diff', or a description or checklist statement that the step was done ('code formatted'), unless the diff contradicts it. Not failures: a check stated nowhere; terse wording; asks to add tests (diff-matches-plan and template-asks-met judge those); process steps that are not runs (signing a CLA, a vouch flow, reading guidelines). | required |
| diff-reviewable | Every hunk of the diff (tests and changelog included) and the commit list, read for debris. See 'Diff quality'. | Pass unless you can quote one of these in the diff's added or re-added lines. (a) DEBUG LEFTOVERS: a debug print, debug logging, or a probe left in, including a commented-out one. (b) COMMENTED-OUT CODE: commented-out code or a kept experiment. (c) DEAD CODE: a function or helper nothing calls, or an allow-dead-code shim. (d) TODO DEBRIS: a stray TODO or note-to-self added. (e) CHURN: import reordering or restructuring, reformatting, re-indenting, or identical lines removed and re-added, in statements the change does not otherwise edit; or an unrelated drive-by edit. Not failures: a comment explaining the fix, or an existing comment updated because the change made it stale; unchanged lines of the statement being edited, shown as removed and re-added (such as a call whose one argument changed); production logging or warnings that the planned behavior calls for; commit messages and commit count, which never decide; tests and changelog entries. | required |
| template-asks-met | The repo-facts block's stated PR-template sections and asks, and its contribution asks (an issue link or closing reference, a changelog or release-note entry, tests added, checklist items), read against the description and the diff. See 'Standards and comms'. | Pass unless you can quote a section or ask the repo states as required that is missing or empty. (a) A required section has no content. (b) A required issue link or closing reference is absent from the description. (c) A required changelog, whatsnew, or release-note entry is absent from the diff. (d) A required test is absent from the diff. (e) A required checklist is missing from the description. Judge substance: content that answers the ask counts under any heading or wording. Not failures: an ask marked not-applicable with a reason; an ask conditioned on something absent ('if appropriate', 'for new arguments', 'for UI changes'); a repo with no stated template or asks; extra sections; ambiguous wording about whether something is required; process obligations that PR text cannot show (signing a CLA, a vouch flow, an approved discussion). | required |
| ai-disclosure-met | The repo-facts block's stated AI policy (its exact words and the stage it names), read against the description for a disclosure sentence. | Pass unless the policy text states that AI use must be disclosed on pull requests, or that all AI use in any form must be disclosed, and one of these holds. (a) The description carries no sentence saying AI assisted the work. (b) The disclosure omits a particular that the policy expressly requires, such as the tool used or the extent of assistance. Not failures: a policy silent on AI, or no stated policy; a policy that asks only for human understanding, human review, or own-words writing without asking that AI use be stated; ambiguous wording; a policy that places disclosure on another stage only (issues, comments); any disclosure sentence that carries the required particulars, however brief. Never infer AI use from style. | required |

## Verdict rule

All eight checks are required; there is no preferred row. Accept when every check passes, or is graded unclear and counted as pass under its rule below. Reject when any check fails, or is graded unclear and counted as fail. The verdict is binary: there is no third outcome and no accept with reservations. Reservations go in evidence lines.

Use unclear only when the recorded facts leave real doubt about whether a fail limb applies. Never use it to dodge a call that the pass condition settles. Read each row's Not-failures list first: a case it describes is a pass. A quoted absence in a test row is a fail, not unclear. Each check treats unclear as follows:

- diff-matches-plan, claims-match-diff, diff-reviewable: unclear counts as pass, because a fault you could not quote did not fire. The exception is when the diff or the plan itself could not be read (a live retrieval failure). Then unclear counts as fail, because nothing was verified.
- fix-shown-before-after, test-plan-covered, repo-checks-run: unclear counts as fail. Each asks whether the package proves its claim, and an unverifiable claim is a failing one.
- template-asks-met, ai-disclosure-met: unclear counts as pass, including when a live retrieval of the template or policy failed (report it as unavailable in the summary). A plainly stated ask or disclosure duty that is left unmet is a fail, never unclear.

Grade and report all eight checks even after one fails. The deciding check is the first check in table order whose grade counts as fail. Each evidence line quotes the deciding fact. For a fail, it also names the limb that fired, such as '(a) ...'. Never fail a check on length, formatting, tone, confidence, or commit count alone.
