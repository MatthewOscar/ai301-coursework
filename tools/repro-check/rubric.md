# Rubric: is this reproduction package ready to post?

Every row below is written as a disqualifier. The default is pass. A row
fails only on named evidence you can quote out of the package itself.

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| environment-recorded | The repro report's environment record — the line or block naming, for THIS reporter's own run, the version or build of the software under test, the platform it ran on, and how it was installed — plus any environment sentence in the claim comment. Read it against the environment the ISSUE places the defect on: the issue's own version and OS lines, any installed-versions or info block it quotes, any statement in its body or ticked template checks that the bug was confirmed on the latest version or on the main branch, and any version a thread comment confirms it on. Live mode: the draft repro comment's environment block against the issue body's environment fields. See "Environment" in references/evidence-guide.md. | Pass unless one of these three is true and you can state it precisely. (a) NO VERSION: the version, build, tag, commit or hosted-instance identifier of the software under test appears nowhere in either draft. (b) NO PLATFORM: no operating system, distribution, platform or hosted environment for this run appears anywhere in either draft. Fail under (a) or (b) equally when the only version and platform facts anywhere in the package belong to somebody ELSE's run — another commenter's machine, the issue reporter's own machine, a screenshot someone else posted — because a borrowed environment records nothing about what this reporter did. (c) STALE BUILD, GAP NOT NAMED: the build under test is OLDER than a build the ISSUE ITSELF places the defect on — the version the issue states, a version its body or its ticked template checks say the reporter confirmed it on, "the latest version" or "the main branch" where the issue says so, or a version a thread comment confirms it on — and no sentence anywhere in either draft names that gap. Quote the issue's build and the report's. Otherwise pass. NOT failures, grade pass: an environment that differs from the issue's on any axis the issue does not place the defect on — operating system, distribution, shell, terminal emulator, install method, architecture, kernel, point release, language runtime — WHETHER OR NOT the report mentions the difference, because an OS or distro line sitting in an issue's routine environment block describes the reporter's machine, it does not pin an axis, unless the issue scopes the defect to that platform in its title, body, labels or thread; a build NEWER than the issue's, including one newer than the version a thread comment confirms it on, since testing forward is the useful direction and tells the maintainer the defect survived — a newer build is never limb (c); a repo "latest release" line newer than the build tested, on its own, because the target is what the ISSUE places the defect on and not what the project shipped last; any difference the report does state, anywhere in either draft and in any wording ("the issue was filed against X, behavior is unchanged on Y", "shell and OS both differ, version matches", "I confirmed it on the Store release", "so it is not specific to debug builds"), including a deliberate change made on purpose and a released binary where the issue's build came from a branch; a missing install method, architecture, kernel, dependency version, build profile, terminal size, display resolution or code-state SHA, none of which this row requires on its own; an environment stated in prose rather than as the pasted output of a version, info or show-versions command, because this row asks whether the facts are on the record and not how they were captured; an environment recorded in the claim comment instead of the repro report, or split across the two; an unreconciled tension between a thread's theory and the versions the run used (a dependency a comment says was already fixed upstream), which is a question to hand the maintainer, not a missing record. | required |
| steps-rerunnable | The repro report's procedure — the commands, inputs, fixtures, configuration files and hand-performed UI actions it says it carried out — read against three things: the artifacts that same report pastes (an output line can prove a step the written procedure never performs), the trigger the issue context describes, and the inputs the issue quotes verbatim, which every reader of this comment already has in front of them. Live mode: the draft's steps against the issue body's reproduction section. See "Steps" in references/evidence-guide.md. | Pass unless one of these four is present and quotable. (a) NO PROCEDURE AT ALL: the report names no command, no input, no keystroke or UI sequence and no action a reader could take, so the only thing a stranger can re-run is the issue itself; a paraphrase of the issue's own hypothesis ("whenever there are tabs in the input", "after a few hours the desktop lags") is not a procedure. (b) DECLARED UNSHAREABLE: the package says an input, fixture, configuration, repository, layout or block list that the DECISIVE run depended on cannot be shared — private, internal, confidential, "I cannot share it" — and offers no shareable equivalent that reproduces, so the positive result exists only where nobody else can go. (c) A STEP THE ARTIFACT PROVES BUT THE STEPS OMIT: quote a line of the report's own pasted output that could only exist if some setup happened which the written steps never perform — a deployed service, a created resource, a pre-existing file or mode — so a stranger following the steps as written lands somewhere the failure cannot occur. (d) DECISIVE INPUT UNREACHABLE: the run the report's conclusion rests on depends on an input, program, fixture, configuration or payload whose trigger-determining content is reachable NOWHERE a reader of this comment can go — not pasted in the report, not quoted or pinned in the issue this comment is posted under, not linked, and not fixed by a stated property that any input carrying it would satisfy. An input a reader can reconstruct exactly from the report's description PLUS what the issue itself quotes IS reachable, whatever the report calls the file it put it in: a wrapper the report describes by naming every parameter the issue already pastes — its input strings, its offsets or indices, its options, its parser — is reconstructible and passes. Otherwise pass. NOT failures, grade pass: an input described by the property that makes it trigger rather than pasted whole, when that property is named and any file carrying it would do (a yaml with one unrecognised top-level section, a multi-line file containing one specific character, four blocks of three lines with no blank lines between them); a fixture the issue itself pastes, re-created by the report from the issue's text and pinned on the properties that matter; scaffolding any reader of that project already has (the HTML around a CDN script tag, a shell prompt, a project quickstart); a SECONDARY or variation run mentioned but not pasted — a repeat count, a padded retry, a sweep across symlink forms — since only the run the report's conclusion rests on is judged here; a step performed in a TUI, GUI or browser and therefore written in prose because it leaves no transcript; a trimmed, elided or excerpt-labelled log when the decisive line is itself shown; a missing cleanup, reset or teardown; terseness — two one-line commands with their output is a complete procedure; no numbered list, no headings, no template fields, no minimal-reproduction repository, no playground link; a step a reader must adapt to their own paths or filenames. | required |
| behavior-matches-issue | The artifacts in the repro report — pasted command output, error text, exit codes, logs, terminal captures, described screenshots, measurements — read line by line against the behavior the issue context describes: its trigger, its observable outcome, its error class and its exit code where it names one, plus the issue's own control or contrast case and any maintainer correction that narrows the trigger. Read together with the sentence in the report or the claim comment that says what the run showed. See "Behavior shown" in references/evidence-guide.md. | Two routes; the package's own words decide which one applies. NEGATIVE ROUTE. When the report states that the behavior did NOT appear — it leads with the non-event, or says plainly in its own words that it could not reproduce, could not reach the reported path, or could not meet a precondition — and pastes the run in which it did not appear, this row PASSES. An evidenced cannot-reproduce is a faithful package. This route short-circuits everything below it: a trigger condition the contributor could not reach is the finding, not a fidelity defect, and nothing in this rubric requires the bug to have been found. Never route a package here that asserts a reproduction; the route is decided by what the package says happened. POSITIVE ROUTE. When the package ASSERTS that the issue's reported behavior was reproduced, seen or confirmed — in the repro report, the claim comment, or both — compare the tested CASE with the issue's before comparing their outputs, then pass unless you can quote one of these five. (a) TRIGGER SWAPPED: the command, input, flag, syntax form, argument value, configuration value, action order or UI action the report ran differs from the issue's on something DECISIVE, and the report does not say it made that change. Decisive means an element the issue's own text, its control or contrast case, or a maintainer's correction in the thread identifies as deciding the outcome — a flag that selects a code path, a separator or sign, a range direction, a syntax form, an operand, the expression under test, a required transition, or a platform the issue scopes itself to and the report never establishes. Quote both strings. A sentence asserting the change was NOT made ("following the report's syntax", "ran it verbatim") is a false fidelity claim, not a disclosure. (b) OUTCOME OF A DIFFERENT CLASS: the artifact's outcome is not the class the issue reports — a validated argument error or usage message where the issue shows a panic, abort or crash; a surviving process and a returned prompt where the issue reports the process dying; a different exit code where the issue names one; a compile-time failure where the issue shows a runtime one; an error where the issue reports wrong output, or wrong output where the issue reports an error; a command that genuinely failed where the issue reports a command that succeeded and was misread. Quote the issue's outcome and the artifact's. (c) ONLY THE PRECONDITION: every artifact shown is setup, version or inventory state — a version string, a session or process list, a successful launch, a config being read, tabs present in a tab bar — and no artifact shows the failing observable the issue names. (d) NO ARTIFACT AT ALL: the report pastes no output, log, capture, measurement or screenshot from its own run, and its whole evidentiary content is a sentence asserting the behavior, including when it leans on somebody else's screenshot or output as if it were its own. (e) THE ARTIFACT SHOWS THE REMEDY: the outcome pasted is the graceful rejection, clamp, validation or correct result that the issue asks for as its FIX, narrated as the defect. Otherwise pass. NOT failures, grade pass: a substitution VISIBLE in the report's own text where the substituted form exercises the same path and the pasted artifact still shows the issue's outcome — an offline or dry-run flag standing in for a verbose one when both print the constructed request, a sibling entrypoint of the same tool, a minimal local file standing in for a remote URL, a config file passed explicitly, a file extension the issue's own prose uses — and the report need not spell out what the issue did instead, only show what it did; a control or contrast run weaker than the issue's, differently shaped, at a different value, or absent altogether, when the FAILING run itself matches; a filename, path, directory, hostname, id or variable name the outcome does not turn on, including one the issue itself spells two ways; a version, OS, shell, install method or build different from the issue's, which is environment-recorded's business and never this row's; an artifact that goes BEYOND the issue (a differential run, a second oracle re-parsing the output, an A or B pair) as long as the issue's own outcome is also shown; a single observation where the issue calls the failure intermittent or a race; a partial, trimmed or excerpt-labelled log that contains the issue's outcome line; a TUI, GUI or visual-state observable reported in prose because it leaves no transcript, PROVIDED some command, capture or verification in the package shows the resulting state; an artifact whose escaping, colour codes or emoji rendering differ from the issue's rendering of the same characters. | required |
| claim-matches-evidence | The sentences in the repro report and the claim comment that say what the run established — the report's Actual line, its summary sentence, and any sentence containing confirm, reproduced, verified, root cause, definitely, exactly, conclusively, 100 percent, or a frequency claim — read against the artifacts the same package pastes. See "Honesty" in references/evidence-guide.md. | Pass unless you can quote a sentence from the repro report or the claim comment that does one of these four. (a) REPRODUCTION ASSERTED, NOT SHOWN: it states that the issue's failure was reproduced, confirmed or observed, while no artifact anywhere in the package shows that failure. (b) CAUSE ASSERTED AS FACT WITHOUT REACHING IT: it states a cause, mechanism or code path as established — "the cause is X", "which is why Y happens", "I verified this is the cause", "this is definitely the Z bug" — when no artifact in the package reaches that code path: no trace, no stack frame, no log line, no file and line number, no instrumented or differential run. (c) FIDELITY CLAIMED AGAINST A QUOTABLE DIFFERENCE: it says the run matched the issue exactly, or followed the issue's steps verbatim, while you can quote a DECISIVE difference (as behavior-matches-issue defines decisive) between what the issue specifies and what the report ran. (d) CONFIRMATION SCOPED WIDER THAN THE BUILD TESTED: it says the issue's defect is confirmed, without qualification, while the run behind it was on a build OLDER than one the issue places the defect on and no sentence anywhere names that gap. Otherwise pass. NOT failures, grade pass: a hypothesis offered as a next step or marked with seems, looks like, suggests, may, appears, "I want to check" — a hedged mechanism is a lead, not a claim; a cause quoted from the issue, the thread or a maintainer and attributed to them; a restatement of a boundary condition the ISSUE itself states, or of what the issue asks for as its fix, which is the issue's claim and not the reporter's; a scope word that holds for the run actually pasted while a neighbouring value went untested ("with exactly one custom header" where the one-header run is shown), which is proof completion, not a false statement; a count of repetitions, extra machines or unshown variations — "I ran this five times", "same on two boxes", "fresh shell", "absolute and relative targets" — which says nothing about WHAT happened and never converts a matching artifact into an overclaim; a report that calls a wrapper it wrote around the issue's own pasted inputs "the issue's script", "the issue's repro" or "the issue's example", where every parameter it names is the issue's own, since the naming is loose but nothing about what ran differs; a provenance sentence a reader cannot audit where the pasted outputs themselves match the issue's; an eyewitness sentence about a TUI, GUI or timing observable that leaves no transcript, when the package's other artifacts corroborate the resulting state; a report that could not reproduce and then reasons about why, INCLUDING a wrong guess at the cause of its own non-reproduction; the word confirmed, or exactly, used about an outcome the package does in fact paste, on a build at least as new as the one the issue places the defect on; an expectation sentence that restates what the issue asks for; an environment delta the package states; enthusiasm, apology, hedging, certainty the evidence earns, or a first-contribution preamble. | required |
| comment-is-usable | The candidate claim comment (the bundle's claim-comment section; live: the student's draft claim comment), read against the issue context it will be posted under — its title, reported behavior, version, and the flags, files, symbols or thread pointers in its body — and against the repro report it ships with. See "Comms" in references/evidence-guide.md. | Pass unless you can quote the claim comment doing one of these three. (a) IT NAMES NOTHING OF THIS ISSUE: the comment names no version, no error string or symptom wording, no flag, file, function, module, setting or subsystem, nothing said in this thread, and no concrete next step — such that the identical text would read the same pasted under any open issue in any repository. Judge only what the comment NAMES. Warmth, frustration, praise, emoji, exclamation marks, urgency and formality are register, and register never decides this limb: a plus-one, a me-too, an "any updates on a fix?" or a paragraph of project praise fails here because it names nothing, never because of how it sounds. (b) IT PROMISES OR RESERVES WHAT THE PACKAGE CANNOT BACK: it guarantees a fix, names a delivery deadline or date, promises a pull request as the committed outcome rather than an investigation, or declares the issue assigned, reserved or held for its author ("keep this issue reserved for me", "assigning myself to this"), or offers an unevidenced claim of mastery of the code as its qualification. (c) IT ASSERTS AN ATTACHED PROOF THAT IS NOT THERE: it says the reproduction, evidence or analysis is below while the attached repro report shows no such thing — quote the comment's sentence and the report's own Actual line side by side. Otherwise pass. NOT failures, grade pass: a short comment, a one-sentence comment, or one that only reports a result on a stated version and names a next step; a greeting, a thank-you, a first-contribution preamble, or an expression of how annoying the bug is, where some other clause names something specific to this issue; declaring a NEGATIVE result in the claim ("I tried to reproduce it before claiming and so far cannot, details below"), which is the honest shape and never a defect; ASKING to take the issue, asking whether it is still open, saying "I'd like to work on this", "I picked this up", "I'd still like to take it", or offering to test someone else's patch; saying "before opening a PR" or "I'll report back" without promising one; a next step that turns out to be the wrong place to look; naming a subsystem the author has not yet read; not mentioning an existing open pull request, a prior failed attempt, an unanswered question, a probable duplicate, or a maintainer's steer — omitting thread context is a missed courtesy, not a defect in the claim; repeating the environment delta in the comment; an AI-assistance disclosure sentence, which is repo-conventions-met's business and never counts against a comment here. | required |
| repo-conventions-met | The repo-facts block's contribution-policy line — its quoted CONTRIBUTING, AI_POLICY or AI_USAGE_POLICY text and the section name it cites — read against the full text of BOTH candidate drafts. Live: CONTRIBUTING.md in the repo root or .github/ and any policy file it links, read against the student's drafts. See "Comms" in references/evidence-guide.md. | Grade this row on the premise that the package is AI-assisted work: that is the workflow this skill exists to check, and it is a property of how the package was produced, not a fact you must find in the bundle. The premise settles ONE question — whether a disclosure sentence was owed — and it never establishes who typed any sentence. Apply each policy clause only to the contribution stage and the activity it names; what is being posted here is a COMMENT on an issue thread, not a pull request. Pass unless BOTH of these hold and you can quote both. (1) The quoted policy contains a sentence REQUIRING that AI use be disclosed, stated or declared — the tool, the extent, or simply the fact of it — in a scope that reaches words posted as a comment on an issue. The archetype is a policy reading that all AI usage in any form must be disclosed, stating the tool used and the extent of the assistance, whose own wording extends to issues and comments. (2) Neither the claim comment nor the repro report contains any sentence disclosing AI assistance. Quote the policy's requirement, then state that no disclosure sentence exists in either draft. A policy that bans the contribution outright also fails this row. Otherwise pass. THESE ARE NOT DISCLOSURE REQUIREMENTS and can never satisfy clause (1): a policy line reading "no stated AI policy", "standard contribution guide", "no stated AI disclosure requirement", or silence on the subject — the absence of a rule is not a rule, and this row never fails a package in a repo with no policy; a policy that WELCOMES or permits AI use subject to responsibility, comprehension, testing, review or explainability duties ("you must review and understand AI-generated content", "only submit code you fully understand and have tested", "be prepared to explain your changes", "fully AI-generated contributions are not accepted", "a human in the loop who understands the work") with no sentence requiring that its use be STATED — a comprehension duty is not a disclosure duty, and no package may be failed for omitting something no rule asks for; a disclosure duty the policy scopes to pull requests, releases or code while this package is an issue comment, including a policy that says in so many words that issue comments carry no disclosure ask; a policy requiring that comments to maintainers be written by a human in their own words and voice, or warning that AI-generated comments may be hidden — an authorship or voice clause is not a disclosure clause, nothing inside a package can prove or disprove who typed its sentences, disclosure would not cure it anyway, and a rubric that failed every package under such a clause would reject the good and the bad alike; a quality warning ("low-quality AI content is closed immediately", "AI-generated pull requests are hard to assess", review time is scarce), which is a warning about burden, not a rule; a template-compliance instruction, however it is worded or wherever it sits ("do not ignore the issue and PR templates"), because unmet template asks are courtesies and the only ones that matter here are already caught by environment-recorded and steps-rerunnable; a CLA, DCO sign-off, first-timer vouch flow, duplicate-search confirmation, latest-version confirmation, or any other requirement that binds at pull-request time or at issue-opening time rather than on a comment; a package that DOES disclose, however briefly, in either draft, whether or not it names a vendor or product; the mere appearance of an AI tool's NAME in the package as the SUBJECT of the bug (a hang while running an AI coding CLI, a workload that triggers the defect), which is subject matter, neither a disclosure nor a violation, and must never be scored as either. Where a single policy carries BOTH a disclosure ask and an authorship or review clause, grade this row on the disclosure ask. | required |
| trigger-isolated | The repro report's second run, where it has one — a control, contrast, differential or A-versus-B run, or an independent oracle applied to the first run's output — read against the issue's own stated contrast case. | Pass when the package contains a second run from the reporter's own machine that isolates the trigger: the issue's contrast case, the same command with the suspected flag or input removed, a pair differing in exactly one variable, or a second tool applied to the first run's output (re-parsing it, piping it to a parser, checking the resulting state with a verification command). Grade unclear when the package pastes only one run, or only the non-event. Fail only when a second run IS pasted and what it shows contradicts the distinction the package claims to have isolated. RANKING ONLY: this row never changes the verdict in either direction. A pass here is the reason to prefer one ready package over another and the first thing to suggest adding to a package that is otherwise ready; an unclear or a fail here never holds a package, and never ask a report that could not reproduce to supply a control it has nothing to control against. | preferred |

Four conventions apply to every row above.

QUOTE OR PASS. Every row is a disqualifier: the default is pass, and a fail
requires a specific sentence, command, output line or policy clause you can
quote out of the package. If you cannot produce the quote, the row passes and
your evidence line says what you looked for and did not find. Suspicion, tone,
confidence, polish and length are not quotes. Certainty language is never a
fail on its own — it is a fail only when you can also quote the artifact that
contradicts it. ONE exception, and it is the only one: in environment-recorded
limbs (a) and (b) the absence IS the quote, so name the field you looked for
across both drafts and did not find.

GRADE THE RUN, NOT THE WRITE-UP. Nothing about the shape of the package may
produce a fail in any row: how many steps it lists, how long or short it is,
whether it uses headings, numbered lists or an expected-versus-actual pair,
whether it follows the repo's issue template, how many template fields it
fills, whether it pastes a version command's raw output instead of stating the
version, whether it links a playground, whether it repeats the issue's own
wording. A terse two-command report with its output pasted is a complete
package; a long, beautifully formatted, certain one can be empty. Unmet
template asks are courtesies, not defects — the only ones that matter here are
those already caught by environment-recorded or steps-rerunnable.

READ THE TWO DRAFTS AS ONE PACKAGE. They post together. A fact stated in
either one counts as stated for every row: an environment delta named only in
the claim comment satisfies environment-recorded, and a disclosure sentence
anywhere satisfies repo-conventions-met. Symmetrically, a claim made in the
claim comment is a claim the report's artifacts must carry, so a comment
asserting a reproduction the attached report contradicts fails even when the
report's own prose is careful.

AN EVIDENCED CANNOT-REPRODUCE IS A READY PACKAGE. This rubric asks whether the
package tells the truth about what happened, not whether the bug appeared. A
report that ran the issue's trigger, did not see the failure, shows what it saw
instead, and names what differed or which precondition it could not meet passes
every row and should be ACCEPTED — that is a result a maintainer wants, and it
narrows where the bug can live. Never fail a row because the bug did not
reproduce, because the report's conclusion is negative, because its Actual line
says "I could not", or because its artifact shows a healthy system. The mirror
of this rule is the one that bites: a package that ASSERTS a reproduction it
does not show fails, however certain its prose and however complete its
formatting.

## Verdict rule

Accept when every check weighted required is graded pass, or is graded unclear
and counts as pass under its own rule below. Reject when any check weighted
required is graded fail, or is graded unclear and counts as fail under its own
rule below. The verdict space is binary; there is no third outcome and no
"ready with caveats" — suggestions for improving an accepted package belong in
the summary, never in the verdict.

Preferred checks never change the verdict. Report trigger-isolated with its
grade; on an accepted package cite a non-pass there as the one thing worth
adding before posting, and never let it hold the package.

How unclear is treated, per check, because the right answer differs by evidence
type.

- environment-recorded: treat unclear as FAIL. The package either names a
  version and a platform for this reporter's own run or it does not, and both
  are fields you can scan two short drafts for; if you are unsure after
  looking, it has not recorded one. Name the field you could not find. Do not
  grade this row unclear because the record is thinner than you would like —
  thin but present is pass. Do not grade limb (c) unclear because you are
  unsure which of two builds is newer: if the issue places the defect on no
  build you can name, limb (c) cannot fire and the row passes on that limb.
- steps-rerunnable: treat unclear as PASS. The row is four named
  disqualifiers, so unclear means the disqualifying evidence is not in the
  package, and a package must never be held for a defect it does not exhibit.
  Grade unclear only when the named evidence is genuinely absent, then pass the
  row and say which of (a) through (d) you could not settle.
- behavior-matches-issue: split, by which route the package put itself on. If
  the NEGATIVE route applies, grade pass and never unclear: an evidenced
  cannot-reproduce has no issue observable in its artifact by construction, and
  uncertainty about whether every condition was covered is not a reason to
  withhold it. If the package asserts a reproduction AND contains at least one
  artifact from the reporter's own run, treat unclear as PASS, because with an
  artifact in hand a real mismatch is quotable and an unquotable one is not a
  mismatch. If the package asserts a reproduction and contains NO artifact from
  its own run, treat unclear as FAIL: limb (d) is already satisfied and there is
  nothing to compare.
- claim-matches-evidence: treat unclear as PASS. A disqualifier row. A sentence
  you cannot map to an artifact, but which asserts neither a reproduction, nor
  a cause, nor a fidelity the run did not have, is not a fail.
- comment-is-usable: treat unclear as PASS. Also a disqualifier row. If the
  package contains no claim comment at all, grade unclear with evidence "no
  claim comment in package" and pass; the repro report is then the whole
  package and the other rows decide it.
- repo-conventions-met: treat unclear as PASS, with one determinate exception.
  Where the policy text cannot be read, or its scope cannot be pinned down, the
  row passes: a repo is never held to a rule nobody can point at. The exception
  is clause (1) itself, which is never unclear on the reasoning that the
  package might not have been AI-assisted — the premise at the top of that row
  settles that question, and where a policy plainly requires disclosure for
  comments and neither draft discloses, both the policy line and the two drafts
  are in front of you, so grade fail.
- trigger-isolated: unclear has no effect, like any grade on a preferred row.

Grade and report every required check, even after one has already failed.
Quote the sentence, command, output line or policy clause that decided each
grade. When two or more required checks fail, name the first in table order as
the deciding reason.

Do not add checks of your own. None of the following may ever produce a fail in
any row: the length, polish, formatting or confidence of the report; a missing
or partly filled repo template; the absence of a control run; the absence of a
raw version-command dump; failing to acknowledge an existing pull request, a
prior failed attempt, a probable duplicate or a maintainer's steer; a
first-contribution preamble; claiming an issue someone else has also claimed;
the reporter's tone, register, warmth or emoji; the package not testing a
version, platform or branch beyond the one it ran; the report offering no root
cause; the bug failing to reproduce; the use of AI in a repo whose policy does
not require that its use be stated; the mere appearance of an AI tool's name as
the bug's subject matter. If a package clears every required check and still
feels wrong, accept it and name the tension in your summary — the fix belongs
in the rubric, not in the run.
